01. Problem Statement

What the city model must solve

Cairo transport network

Congestion

Road weights change by time period, capacity, and road condition. A static shortest path is not enough for realistic routing.

Emergency routing

Ambulance paths must favor faster travel and priority intersections while still finding a valid hospital target.

Fleet allocation

Routes and buses are limited resources, so passenger coverage has to be optimized under capacity constraints.

Why this matters

  • Travel time must adapt to real traffic profiles rather than distance alone.
  • Emergency response needs priority-aware routing and intersection overrides.
  • Resource planning must maximize passengers served per available vehicle or trip window.

Project objective

Unify routing, traffic, and allocation logic in one modular system so each algorithm solves a specific operational decision on the same transport graph.

06. Dijkstra Algorithm

Baseline shortest-path engine for static routing

shortest path
dist[v] = min(dist[v], dist[u] + w(u, v))
  • Definition: finds the least-cost path from one source to one destination on a non-negative weighted graph.
  • Why used: provides the baseline route in the service layer and a fair comparison point for A*.
  • Role in project: RouteService uses Dijkstra for the standard shortest route mode.
  • Complexity: O(E log V) time and O(V) space in the implementation metadata.

Implementation details

  • Uses a priority queue from heapq.
  • Tracks explored nodes with nodes_explored.
  • Consumes the shared CostEvaluator for edge weights.
  • Reconstructs the final path from the predecessor map.
In benchmark mode the shared cost evaluator can keep the comparison fair by using static road distance.
Source: Backend/algorithms/shortest_path/dijkstra.py

07. A* Search Algorithm

Heuristic-guided routing for faster emergency decisions

heuristic search
f(n) = g(n) + h(n)
  • Definition: balances the cost so far with a heuristic estimate to the nearest goal.
  • Heuristic used: Euclidean distance to the closest goal position, scaled to stay admissible when priority discounts are present.
  • Role in project: used by EmergencyService to route toward the nearest reachable medical facility.
  • Complexity: O(E log V) time and O(V) space in the implementation metadata.

What the code tracks

  • Goal positions: the graph stores facility coordinates for multi-goal routing.
  • nodes_explored: explicit counter used in testing and evaluation.
  • Time awareness: optional initial time feeds the shared cost evaluator.
  • Emergency support: base emergency multiplier plus intersection priority scaling.
The heuristic is not a generic guess: it is the minimum Euclidean distance to any valid goal in the graph.
Source: Backend/algorithms/shortest_path/astar.py

09. Dynamic Traffic Weight Logic

How the system turns traffic data into route cost

dynamic cost model
w(u,v,t) = d(u,v) * (1 + (flow/capacity)^2) * (11/condition)
cost = base_weight * emergency_multiplier * congestion_index
  • Time periods: morning peak, afternoon, evening peak, and night are mapped from clock time.
  • Condition effect: a lower road-condition score increases travel cost.
  • Congestion effect: flow is normalized by capacity and squared to amplify heavy congestion.
  • Emergency effect: default global multiplier is 0.8, with stronger intersection discounts via IntersectionPriority.

Why this is academically important

  • Realism: dynamic weights reflect road condition and traffic variation instead of fixed distances.
  • Fair comparisons: the shared evaluator can switch between benchmark and realistic modes.
  • Emergency routing: the same framework can prioritize ambulance travel without rewriting the graph.
This is the actual cost logic used by Edge.get_weight() and CostEvaluator.edge_weight().
Time-aware costs are central to the routing model

11. 0/1 Knapsack Solution

Exact DP for route selection and fleet usage

exact optimization
DP[i,w] = max(DP[i-1,w], v_i + DP[i-1,w-w_i])
  • Definition: choose each route at most once while respecting total capacity.
  • Why used: greedy selection can miss the global optimum when passenger value and bus usage conflict.
  • Implementation role: ResourceAllocationDP builds a 2D DP table and reconstructs the chosen routes.
  • Complexity: O(n * capacity) time and space in the current implementation.

What the code actually stores

  • weights: bus counts per route, clamped to at least 1.
  • values: passenger demand per route.
  • dp table: rows are items, columns are capacity states.
  • output: selected routes, total passengers covered, and a schedule dictionary.
Source: Backend/algorithms/dp/resource_allocation.py

12. Dynamic Programming Table Logic

SchedulingDP is weighted interval scheduling

compatibility DP
dp[i] = max(value_i + dp[p(i)], dp[i-1])
  • Correction: the current implementation is not knapsack; it schedules non-overlapping trips.
  • Workflow: parse times, create intervals, sort by finish time, binary-search the last compatible trip.
  • Role in project: selects the best passenger-heavy trip subset without overlap.
  • Complexity: O(n log n) time and O(n) space.

Why this matters

  • It respects time compatibility instead of treating trips as independent items.
  • Binary search keeps compatibility lookup efficient.
  • Backtracking reconstructs the final schedule in route-by-route form.
This correction is important for academic accuracy because the file name can mislead readers.
Source: Backend/algorithms/dp/scheduling.py

13. Greedy vs DP Comparison

Speed of local choice versus global optimality

decision quality
Greedy

Traffic signal optimizer

Chooses the busiest incoming road at each intersection and assigns it the longest green phase. It is fast and suitable for live control.

  • Local maximum by incoming flow.
  • Used for real-time signal plans.
  • Can miss a globally optimal citywide schedule.
Dynamic programming

Resource allocation and scheduling

Evaluates combinations or compatible intervals to maximize passenger coverage. It is slower, but the result is provably optimal for the model.

  • Global optimum under constraints.
  • Best for planning and allocation.
  • Matches the academic objective of exact optimization.

Best use case

Greedy is the right fit for immediate traffic-light response, while DP is the right fit for offline planning when a full search is acceptable.

Project takeaway

The repository intentionally uses both approaches because the city problem contains both fast operational decisions and exact planning decisions.

Different subproblems need different optimization styles

17. Scalability and Optimization

How the system can grow without changing the core model

future-ready architecture

More districts

GraphBuilder and TransportGraph can scale to larger node sets as long as the processed CSVs are expanded consistently.

Better traffic intelligence

TrafficMLService can be used to forecast next-flow values, then feed calibrated congestion inputs into the cost evaluator.

Modular extensions

Additional routing policies or transit modes can be added without rewriting the graph layer or model classes.

Optimization directions

  • Cache repeated route queries for common origin-destination pairs.
  • Precompute or index critical hospitals and hubs for faster emergency lookup.
  • Calibrate dynamic weights against updated traffic observations.

Algorithmic extensions

  • Add multi-objective routing with safety or emissions as extra cost terms.
  • Expand planning to larger MST or network-design scenarios.
  • Integrate the simulation outputs into a live dashboard.
